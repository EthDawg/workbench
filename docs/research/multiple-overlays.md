# Workbench: prepared presentation overlays

Research checked **15 September 2026**. Primary vendor/platform documentation only; no installs, accounts, hands-on competitor tests or meeting receiver observations. Local baseline inspected at `8fdf02a` plus the current working tree. The comparison records the pre-build recommendation; the final section describes the implemented increment. The linked source specification owns current validation and release status.

**Recommendation:** extend the existing native overlay into a deliberately prepared presentation set, with several independently positioned items and a compact session controller. Start with artwork/text over the real apps the presenter already operates. Add page-aware browser behavior or captured app-window composition only when the required sharing route makes it necessary.

## First distinguish three meanings of overlay

| Job | Where it actually lives | Practical consequence |
| --- | --- | --- |
| A persona, logo, caption or pointer above the browser and other Mac apps | Workbench-owned transparent native windows | Browser remains interactive when artwork is locked/click-through. Screen coordinates do not automatically follow a scrolling page or a DOM element. Whole-display sharing is the initial supported route to validate. |
| A callout attached to a particular web page or element | Browser extension content injected into that page | Can follow page scrolling/layout and appear inside a shared tab. Needs browser permissions, navigation handling and testing in the supported browsers. Native app windows cannot supply this behavior by themselves. |
| Several live apps or browser windows arranged inside one presentation | Captured sources composed in a Workbench output window | A distinct source/capture job: permissions, unavailable windows, crop, refresh and lifecycle. Captured video does not itself provide remote input; keep interaction in the original apps. Share the composed output window. |

The first is the smallest extension of Workbench. It can switch prepared overlays while the user changes tabs manually, without a browser extension. If “multiple tabs” means simultaneously showing several live tab contents, that is the third job or a browser capture integration—not extra image overlays.

## Top three interaction primitives to borrow

1. **Prepare a named set; switch only its allowed choices.** In the normal app, add/reorder a few audience-safe items and prepare ordered cues that specify which are visible and where. A cue may show several items simultaneously. Starting creates a live snapshot; library browsing and later edits do not silently change it. A clear Next/Previous or selected-cue action commits the change. Include public cue labels in the controller, not other customers' saved names. This adapts OBS's preview/live separation and collections without requiring two large canvases. Existing persona groups already supply the confidentiality pattern.

2. **Lock to demonstrate; explicitly edit to arrange.** Keep artwork click-through during normal use. Expand the compact controller to select an item, show/hide it, or enter placement editing; offer native order/position commands alongside drag and snap. Return immediately to interaction with the original app after editing. Use one action catalogue for buttons, menu bar and configurable shortcuts; contextual next/previous keys must not consume ordinary app typing outside the session. DemoPro's momentary flow, PerfectPixel's lock and Presentify's scoped keys are the useful pieces—not their entire tool palettes.

3. **Hide all now; end only this session.** Hide all is reversible and immediate. End dismisses this session's artwork/controller, stops only its capture/animation resources and releases its temporary keys. Saved sets survive. It must not close the customer's browser, stop an unrelated dictation, restore wallpaper, or leave a transparent input-blocking layer behind. Keep End visible in expanded controls and available from the menu. Escape should first leave an editor/menu consistently; a separate assigned Hide all command avoids ambiguity. No startup auto-display.

Motion should communicate one change: a short optional dissolve between safe overlays, temporary ink fading, or drag/snap feedback. A transition must never delay Hide all/End; stop hidden animations. Use a cut for customer/context changes so old artwork cannot linger. Default to system control animations and honor Reduce Motion; do not animate every cue label or continuously move text. This follows [Apple's motion guidance](https://developer.apple.com/design/human-interface-guidelines/motion?changes=l_9_3), whose current change log includes 9 September 2025. Exact timing should be judged in native/receiver testing rather than presented as an established optimum.

## Sharing and platform boundaries

| Delivery route | Documented support | What Workbench can safely claim/design |
| --- | --- | --- |
| Whole display | [Teams](https://support.microsoft.com/en-us/teams/meetings/present-content-in-microsoft-teams-meetings) and [Zoom](https://support.zoom.com/hc/en/article?id=zm_kb&sysparm_article=KB0060596) offer display sharing. | Visible native artwork is part of the displayed desktop. Assume the HUD/menu may also be visible; use a second unshared display or collapse it. Workbench cannot advertise a private presenter controller merely by setting a window flag. |
| Individual or selected windows | Zoom documents Shift-selecting multiple applications on Mac. Teams documents an opt-in native macOS sharing experience; its give/take-control feature is unavailable in that mode. | Separate artwork is not automatically part of the browser's content. Selected extra windows may provide a workable route, but receiver verification is required for each client/mode. A Workbench composition includes its own artwork pixels by construction. |
| Browser tab | Zoom web offers tab/window/desktop; [Teams' screen-reader guide](https://support.microsoft.com/topic/55cbbb3e-1f02-4d71-ac52-7341ea6262b7) describes Chrome Tab sharing. | A native window above a tab is not page content. A page-injected overlay could be included; validate it rather than promising inclusion for every capture implementation. |
| Capture into a Workbench composition | Apple's [ScreenCaptureKit picker](https://developer.apple.com/videos/play/wwdc2023/10136/) supports user-selected windows, apps and displays, stream replacement, cancellation and per-stream exclusions. | Reuse the system picker if actual captured sources are needed. Its exclusions govern Workbench's stream, not what Teams/Zoom independently capture. Do not ask for capture permission just to draw imported artwork. |
| Page-aware browser extension | [Chrome content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts) can modify permitted pages. [`activeTab`](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab) grants temporary user-invoked access and is revoked across origins or tab closure. | Begin with explicit per-tab activation if the need arises; persistent page rules need deliberate permissions and navigation rules. Handle route/scroll/zoom/frame changes; never infer an active customer from hostname alone. Safari/Firefox would need their own packaged integrations and validation. |

For live tab video, [Chrome tabCapture](https://developer.chrome.com/docs/extensions/reference/api/tabCapture) is a separate permission/capture API with invocation and stream-lifetime rules. Do not add it for simple page annotations. Avoid remote websites in a new embedded browser as a substitute for the user's authenticated browser/profile.

## Current source seams and smallest next step

- `Persona.swift:422–437` currently shows/hides **one** overlay and freezes a prepared group's allowed candidates; `479+` builds its HUD from that scope. `PersonaOverlay.swift:4–22,38–47` supplies a non-key/non-main native panel with click-through locking. This is reusable window behavior, not a current multi-overlay session manager.
- `PersonaHUD.swift:26–31` makes the controller key only for explicit keyboard access. `PresentationControls.swift:3–25` has deliberate reveal/Escape ownership. Reuse those conventions and the existing floating placement/guide helpers; avoid attaching voice/model controls to the presentation HUD.
- `DemoScenes.swift:344–359` permits one active device presentation and hides the separate persona. `DemoPresentation.swift:11–25` snapshots scene/assets; `54–74` ends capture and owned resources. A new general overlay set must not silently alter that existing lifecycle or claim those controllers already support arbitrary live apps.
- `docs/product-spec.md:57–65` owns current sharing/group rules; `site/handbook/contract.json:205–207` marks meeting receiver verification **not run**. The new session behavior should amend the owning contract after agreement, not become another parallel roadmap.

**Smallest useful increment:** two imported/copy-rendered items visible at once, two prepared cues, explicit Start, compact Next/Previous + Hide all, expanded per-item visibility/lock/placement + End, all scoped to the selected set/display. Keep set persistence separate from ephemeral session state and preserve source assets. No automatic tab tracking, capture engine, extension, virtual camera, tenant switching or team service in that increment.

Before claiming success, run one synthetic browser demo in two tabs and one native app: show two items, switch cues, edit/lock, hide/restore, end, and verify original app input still works. Test display removal, lost source, repeated End and edits to a running set. Then observe a receiver in Teams and Zoom for whole-display, selected-window and browser-tab modes, with the expanded controller visible. Those observations decide whether an extension or composed output is actually required.


## Implementation decision and review

The increment uses a group-owned prepared layout plus a bounded, frozen live session in StageKit. There is one click-only native control tile, separate per-copy state and explicit layout saving. Five optional hotkeys use the existing Keyboard page and start disabled. A 0.16-second soft reveal is opt-in, only for newly shown artwork, and respects Reduce Motion. No new server, browser extension or cloud schema was introduced.

Native review caught and corrected same-level artwork covering its controls, empty working sets becoming unreachable, and failed live saves lacking feedback. The tile sits above its own artwork, empty sets remain revisitable, and public-safe notices stay visible until the next action or dismissal. Private diagnostic details stay in preparation.

The guide and source specification own the exact current validation and delivery boundary. Research is documentation-based; the native tests exercised Workbench with disposable content, not competitor products. The prior guides were archived before material edits.
